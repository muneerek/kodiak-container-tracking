# User module following your proposed structure

`007_user_structure_proposal.sql` is a **standalone review design** in the `user_design` schema. It can run without previous scripts. It does not migrate or replace existing `kodiak.users`, UUID references or the permission model. Do not run two competing authentication stores in the production application. No EF code is generated.

| Requested table | Purpose |
|---|---|
| userDetails | User identity, credentials, business type and status |
| userLoginDetails | One row per successful login session; logout updates that session ID |
| userTokens | Hashed refresh, password-reset and email-verification tokens |
| userRoles | Dynamic role master; no hard-coded role-name restriction |
| userRoleMapping | Additional junction allowing multiple roles per user and many users per role |

## PostgreSQL adjustments

- `identity(1,1)` becomes `GENERATED ALWAYS AS IDENTITY`, starting at 1 and incrementing by 1 by default.
- `nvarchar` becomes `varchar`, and `nvarchar(max)` becomes `text`. Create the database with UTF-8 encoding for multilingual text.
- `datetime` becomes `timestamptz`; `bit` becomes `boolean`.
- PostgreSQL primary keys get unique indexes, but there is no SQL Server-style `PRIMARY KEY CLUSTERED` declaration. No physical clustering is configured.
- User IDs, login IDs and token IDs use `bigint`; role IDs use `integer` as requested. Foreign keys use the same types as the referenced keys.
- `createdBy` and `updatedBy` use nullable `bigint` foreign keys rather than text. Null permits initial bootstrap and unauthenticated registration.
- Your camel-case names, including `createOn`, are preserved with quoted identifiers. Example: `SELECT "userId", "userName" FROM user_design."userDetails";`.
- Every table includes the four audit columns, including login history and role mapping. Triggers stamp actor/time from transaction-local `kodiak.actor_id` supplied by the trusted API, not by request-body values.

## Proposed code meanings

| Column | Value | Meaning |
|---|---|---|
| userType | 1 | Normal/internal Kodiak user; not automatically an administrator |
| userType | 2 | Consignee user |
| userType | 3 | Shipper user |
| userStatus | 1 | Active |
| userStatus | 2 | Terminated |
| userStatus | 3 | Suspended |

These business categories do not replace dynamic roles. Role codes/names remain configurable. Role permissions and company membership still need integration from the existing design before this module is production-ready; the minimal mapping here does not enforce company-type-compatible roles. Public registration must never let users assign themselves roles, active approval, or internal-user status.

`userPassword` retains your column name but must hold only the password hash generated by the backend password hasher. No plaintext passwords. `userTokens.tokenhash` also stores a hash, never the raw token. API must enforce account status, lockout, verification policy, token expiry and atomic consumption. Null logoutTime means no logout was recorded, not necessarily an active session; browser closure/expiry may leave it null.

Next design integration will replace the old user references across bookings, audit, role permissions and other tables with this naming and numeric-ID convention, and then regenerate the full diagram. The existing 29-table diagram still describes the previous complete schema, not this isolated proposal.
